The Daily Fit

A Wordle-style fashion puzzle, scored by semantic similarity.

§1 The Problem

Shopbop sells fashion; the capstone brief asked for a daily habit to match — a guessing game where the score isn’t letter colours but closeness of taste. Judging “semantically similar” between outfits is exactly the kind of problem humans argue about and vector search doesn’t. It also had to persist streaks, or a daily game is just a page refresh away from forgetting you existed.

§2 The Architecture

A web client talks to a serverless AWS spine: API Gateway fronts Lambda functions that generate the daily puzzle, score every guess through Shopbop’s vector search API, and persist puzzles, guesses, and streaks in DynamoDB. No servers, no schedules to babysit — the game is data, and the data is small.

§3 The Tradeoffs

Serverless is the right tradeoff because the load is a daily spike, not a stream — cold starts matter less than a zero-ops bill. One DynamoDB table holds puzzles, guesses, and streaks; denormalizing around known access patterns beat a relational schema for this. And the similarity judge lives in Shopbop’s own vector search API, which means we inherit their notion of style — for a fashion product, that is the correct dependency to have.

Trail Lab

PDF question-answering and multilingual audio, at conversation speed.

§1 The Problem

Trail Lab’s knowledge lives in PDFs and recordings — papers, field notes, interviews. Search finds documents; it doesn’t answer questions. And every change waited on a fifteen-minute deploy, which is how CI quietly becomes a tax on shipping anything at all.

§2 The Architecture

Two FastAPI pipelines under one Next.js front end. PDFs are chunked, embedded, and stored so retrieval returns context in under 0.2 seconds, with Groq models doing the answering. Audio runs through Groq for transcription, summarization, and translation across 10+ languages. CI/CD moved to GitHub Actions with GCP Cloud Build, gated by test suites.

§3 The Tradeoffs

Groq-hosted inference trades control for speed — I’d rather tune retrieval than babysit GPUs. The 0.2-second budget shaped the architecture more than any model choice: embeddings are precomputed and the retriever stays deliberately simple. And the deploy went from fifteen minutes to two, which changed behaviour more than any feature — fast CI actually gets run.

Badger Code

A Qwen coding agent, graded honestly on 89 terminal tasks.

§1 The Problem

Coding agents fail in ways that are hard to see and harder to reproduce. The question was never whether Qwen could write code — it was how often it could finish a real terminal task, in a sandbox it can’t escape, measured the same way every single time.

§2 The Architecture

A Qwen-powered coding agent runs autonomous shell workflows through Harbor, each attempt inside its own isolated Docker environment. A reproducible Terminal-Bench pipeline evaluates across 89 tasks, tracking every action the agent takes and scoring completion honestly: 40+ of 89 finished end-to-end.

§3 The Tradeoffs

Isolation is expensive — a container per attempt is slower than sharing a machine — but it’s the only configuration where a benchmark means anything. Terminal-Bench over a custom suite, because a standard everyone can check beats a leaderboard only I can verify. And the failures are kept, not hidden; the unfinished tasks are the interesting part.

MERRA-2

Five hundred gigabytes of atmosphere, taught to behave.

§1 The Problem

The Department of Atmospheric & Oceanic Sciences sat on 500GB+ of NASA MERRA-2 reanalysis data and a stack of ensemble models that were neither fast nor consistently accurate. Analysis was manual, and experiment workflows varied by whoever happened to run them.

§2 The Architecture

Feature engineering and ensemble optimization in Python — Pandas and NumPy for the heavy lifting, scikit-learn for the models — with automated processing and visualization pipelines replacing the manual loop. Cross-validation was formalized so every experiment is comparable. Accuracy improved 15%; manual analysis time halved.

§3 The Tradeoffs

Ensembles over deep networks: the data is wide, tabular, and expensive to move, so the wins came from features and validation rather than architecture heroics. scikit-learn over PyTorch here is a deliberate downgrade in fashion and an upgrade in honesty — every result cross-checked, every pipeline reproducible by the next student in the lab.

Educate Nepal

A non-profit platform, ten thousand readers strong.

§1 The Problem

The Educate Nepal Initiative needed a real platform — 10K+ monthly users, authentication, content, a database that doesn’t fall over on the day it matters — with a non-profit budget and a volunteer engineering team of one.

§2 The Architecture

A three-tier platform: React + TypeScript front end, Node.js APIs, PostgreSQL — on AWS. I owned the database design, authentication, backend APIs, and cloud deployment end to end, schema to DNS, and architected it to stay legible to whoever maintains it after me.

§3 The Tradeoffs

One volunteer owning the whole stack isn’t good architecture on paper; it’s what a volunteer budget buys, and it holds up at ten thousand readers a month. Postgres over a managed PaaS database kept costs near zero and the schema auditable. AWS over shared hosting, because a non-profit’s worst outcome is being down on the day it matters.

Every layer chosen to be boring on purpose: relational data, stateless APIs, one cloud. The interesting decisions were the schema and the auth flow — everything else is plumbing that stays out of the way.

BadgerRides

Ride matching for Badgers, with a chat that keeps up.

§1 The Problem

UW–Madison students coordinate carpools in group chats: rides buried under memes, no matching, no record of who’s going where. BadgerRides gives the campus a purpose-built platform — ride matching, profiles, and a chat that behaves like chat should.

§2 The Architecture

A React + TypeScript client over a Node.js/Express REST API, PostgreSQL as the source of truth, JWT for stateless authentication, and Socket.IO for real-time messaging — each ride is a room, and every message is scoped to the carpool you’re actually in.

§3 The Tradeoffs

Socket.IO over polling trades connection management for an interface that feels live — the right tradeoff for chat, the wrong one for anything a user can afford to refresh. JWT keeps the servers stateless and horizontal scaling boring. Ride matching lives server-side, where it can be tested, not in the client, where it can be faked.
